# AgenticRAG v0.8 — 用户请求全流程追踪

> 面试讲述模板：从用户在 Gradio 输入框按下回车，到答案出现在屏幕上，中间发生了什么。

---

## 全景时序图

```
0ms     用户按下回车
        │
~1ms    [前端] 输入框立即清空，消息加入聊天历史
        │
~2ms    [安全层] 限流器检查 → 通过（未超60RPM）
~3ms    [安全层] RBAC 不做过滤（单用户demo模式）
        │
~5ms    [缓存层] CacheManager.get()
        │  ├─ L1 精确缓存: MD5("What are the file upload limits...") → 未命中
        │  └─ L2 语义缓存: FAISS 搜索相似问题向量 → 未命中
        │
~10ms   [Agent层] 进入 LangGraph 工作流
        │
        ├─ [Node 1] classify_intent ─────────────────────── 2-5s (LLM API)
        │    Prompt: "Classify the following question..."
        │    LLM 返回: "simple"
        │    state.intent = "simple"
        │    → 推理轨迹: "[classify_intent] 意图: simple"
        │
        ├─ [Node 2] retrieve ───────────────────────────── <100ms (本地)
        │    1. _get_current_query() → state.question
        │    2. FAISS 稠密检索: 60,818 个向量中取 top-100
        │    3. BM25 稀疏检索: 60,818 篇文档中取 top-100
        │    4. RRF 融合 (k=60): FAISS top-100 + BM25 top-100 → 去重排序
        │    5. 截取 top_k=5, 去重合并到 accumulated_chunks
        │    → 推理轨迹: "[retrieve] 检索到 5 篇"
        │
        ├─ [Node 3] rerank ─────────────────────────────── ~1.5s (GPU/本地)
        │    CrossEncoderReranker.rerank(query, 5 chunks)
        │    - 每篇截断到 512 字符
        │    - bge-reranker-base 逐对打分
        │    - 按精排分降序, 保留 top-5
        │    → 推理轨迹: "[rerank] 精排: 5→5 篇"
        │
        ├─ [Node 4] check_sufficiency ──────────────────── 2-5s (LLM API)
        │    Prompt: "根据文档判断是否足以回答..."
        │    LLM 返回: "SUFFICIENT"
        │    → 推理轨迹: "[check_sufficiency] 充分"
        │
        └─ [Node 5] generate_answer ───────────────────── 5-15s (LLM 流式)
             Prompt 注入:
             - 对话历史（如有）
             - 检索到的 5 篇文档全文
             - 用户原始问题
             LLM 逐 token 流式返回
             → 推理轨迹: "[generate_answer] 答案生成完毕"

~15s   [安全层] PII 脱敏
        │  扫描答案中的邮箱/电话/薪资关键词
        │  mask 模式: 替换为 "***"
        │
~16s   [安全层] 审计记录
        │  写入 logs/audit_2026-07-13.jsonl:
        │  {"timestamp":"...", "user_id":"default", "question":"What are...",
        │   "intent":"simple", "answer_length":342, "sources_count":5,
        │   "from_cache":false, "cache_type":"none"}
        │
~17s   [缓存层] CacheManager.put()
        │  L1: 问题MD5 → {answer, intent, sources}
        │  L2: 问题向量 → {answer, vector}
        │
~18s   [前端] 答案展示完成
        │  左侧: 完整答案 + "[来源1][来源2]..." 引用
        │  右侧: Agent 推理轨迹 + 检索来源面板
        │  答案下方: 缓存状态标记（如有）
```

## 各节点详解

### Node 1: classify_intent（意图分类）

**做什么**：判断问题属于 simple / multi_hop / unclear 中的哪一种。

**LLM Prompt 精简版**：
```
'multi_hop' ONLY if truly needs MULTIPLE DIFFERENT documents.
'and' alone does NOT make it multi_hop.
```

**输出示例**：
- "What are file upload limits?" → `simple`
- "Compare 2021 and 2022 revenue growth" → `multi_hop`
- "那个公司怎么样？" → `unclear`

**关键设计**：保守策略——默认判 simple，只有明显跨文档推理才走 multi_hop。避免误判导致不必要的子问题拆解和 retry 循环。

---

### Node 2: retrieve（混合检索）

**做什么**：从 60,818 个文档 chunk 中找到与问题最相关的 5 个。

**检索流程**：
```
用户 Query
    │
    ├─→ FAISS Dense Search (语义匹配)
    │   query → bge-base-en-v1.5 → 768维向量
    │   → IndexFlatIP.search(top_k=100)
    │   → [(chunk_id, cosine_sim), ...]  ×100
    │
    ├─→ BM25 Sparse Search (关键词匹配)
    │   query → 分词 → BM25Okapi.get_scores()
    │   → [(chunk_id, bm25_score), ...]  ×100
    │
    └─→ RRF Fusion (k=60)
        score(chunk) = 1/(60+FAISS_rank) + 1/(60+BM25_rank)
        → 去重排序 → 截取 top_k=5
```

**为什么两个都要**：FAISS 能理解 "upload" ≈ "file transfer"（语义相近），BM25 能精确匹配 "dp-132-usw"（专有名词）。

---

### Node 3: rerank（Cross-Encoder 精排）

**做什么**：bi-encoder 粗筛后，用更精准的 cross-encoder 二轮打分。

**为什么需要**：bi-encoder 把 query 和 doc 分别编码——速度快但精度有损。cross-encoder 把 (query, doc) 拼成一对打分——精度高但速度慢。所以先粗筛再精排。

**模型**：BAAI/bge-reranker-base

**容错**：模型未下载时自动跳过，日志告警但不阻塞流水线。

---

### Node 4: check_sufficiency（充分性校验）

**做什么**：LLM 自己判断检索结果是否足以回答问题。

**渐进式宽松策略**：
```
retry 0 → 严格: "关键事实缺失 → INSUFFICIENT"
retry 1 → 温和: "有部分信息能给出有用回答 → SUFFICIENT"
retry 2+ → 自动通过 (不做 LLM 调用)
```

**为什么这样设计**：防止"列出所有子公司"这类穷举型问题永远判 insufficient 导致死循环。

**输出示例**：
- `SUFFICIENT` → 进入 generate_answer
- `INSUFFICIENT: missing 2022年的研发支出数字` → 进入 refine_query

---

### Node 5: generate_answer（答案生成）

**做什么**：综合检索文档 + 对话历史，生成最终答案。

**Prompt 结构**：
```
[对话历史: 用户问了X, 助手答了Y]
[检索文档: [chunk_1] ..., [chunk_2] ...]
[用户问题]
→ 流式生成答案
```

**流式输出**：逐 token yield 到 Gradio 前端，用户看到答案逐字出现。

**引用标注**：生成后正则替换 `[doc_1234]` → `[来源3]`，对应右侧来源面板的编号。

## 错误处理与降级策略

```
缓存不可用    → 跳过缓存，走完整流水线
LLM 主供故障  → DeepSeek → OpenAI → Anthropic 三级 fallback
精排模型未下载 → 跳过精排，保留粗排结果
Redis 不可用   → 降级本地内存 (限流/RBAC/缓存)
索引文件缺失   → 启动时打印警告，不影响服务启动
单节点异常     → try/except + 日志，不中断整个流水线
```

## 面试讲述建议

**30 秒版本**（电梯 pitch）：
> "用户输入问题后，系统先做限流和缓存检查——如果 30 分钟内有人问过同样的问题，直接返回缓存答案。没命中就走 Agent 工作流：意图分类判断简单还是复杂，混合检索找到相关文档，精排器二轮排序，充分性校验判断信息够不够——不够就改写查询重试，够了就流式生成答案。答案返回前做 PII 脱敏和审计记录，同时写入缓存供下次复用。"

**3 分钟版本**（对着架构图讲）：
> 从顶部到底部，按安全层→缓存层→Agent层→检索层→数据层的顺序，每个节点一句话讲清楚输入输出和关键设计决策。重点强调三个地方：
> 1. 渐进式充分性校验（防止死循环）
> 2. FAISS+BM25 互补（语义+关键词）
> 3. 两级缓存（L1精确100ms + L2语义200ms）
